# Security and persistence model

## Network and public metadata

SafeHttpFetcher uses Node HTTPS directly, without a proxy or pooled socket. It resolves all candidate A/AAAA addresses, rejects empty/oversized sets and every special-use address, chooses a checked address, and supplies it through the actual TLS socket's lookup callback. TLS hostname/certificate validation stays enabled for the original hostname. The socket cannot re-resolve the hostname after inspection. Redirects and nonidentity compression fail; the implementation requests identity encoding and rejects compressed responses before processing, so decompression cannot bypass the 64 KiB limit. Content type, status, strict UTF-8, BOM, JSON duplicates and nesting are checked. CIMD+JWKS share a 10 second total retrieval deadline. Per-process concurrency is 8 globally/2 per origin; no queue grows without bound.

Test-only CA/address/resolver injection requires `NODE_ENV=test`, permits only explicitly named loopback destinations and checks every DNS answer against that destination list. Production entrypoints reject test network configuration, test mode and disabled TLS verification. Tests use an actual UDP DNS server that changes its answer and emits mixed addresses, and real hostname-validated TLS sockets. These exceptions are confined to fixtures.

Metadata/key cache is bounded to 256 exact client IDs and 60 seconds. An unknown kid permits at most one refresh for that authentication attempt. Cache failures never retain expired keys, and cache eviction never removes bans. The raw CIMD digest and raw JWKS digest are distinct SHA-256 values; the RFC 7638 public-key thumbprint is distinct again. Metadata snapshots remain fixed during an authorization and are time-checked immediately before COMMIT, after all SQL work and lock waits. Issuance, revocation and verified denials roll back atomically if that final proof window has expired.

Before fetching untrusted metadata, PostgreSQL atomically consumes explicitly configured issuer-wide, origin, claimed-client and source-address minute budgets. Global comes first, so a rejected global flood cannot allocate unbounded attacker-named buckets. All AS replicas use the same rows/lock; in-process authentication/fetch concurrency are additional cost bounds. Socket source is used without trusting forwarded headers. A reverse proxy must provide perimeter rate limiting appropriate to its topology. Database pool size/connect/statement/lock deadlines are bounded.

## PostgreSQL authority

No Map is an authority for clients, grants, tokens, replay, bans or quotas. The migration creates only machine-profile state, including independent RS secret digests. Client uniqueness is `(issuer SHA-256 namespace, exact client_id)` and the machine subject is a stable UUID. Random 256-bit opaque tokens are returned only after transaction commit; only SHA-256 token digests persist. Agent private keys and full assertions are never stored. High-entropy RS secrets are operator-injected and stored as digests.

The transaction lock order is client advisory lock, resource policy row lock, then client/grant/token writes. Issuance and ban/revocation administration use the same client lock. Policy changes advance a generation without scanning clients. Current client/grant/policy generation, enabled state, blocks, token expiration and revocation are checked together on every introspection. New key snapshots never change the machine subject. Re-enabling a client does not reactivate prior-generation tokens. A disabled exact grant cannot silently be recreated by the next request.

Replay uniqueness is `(namespace, client_id, jti digest)` across resources. Retention ends only after assertion expiration plus clock tolerance. Verified final denials commit replay and a bounded category audit event. No failure retry is hidden in the store. Lost COMMIT acknowledgement is an uncertain issuance outcome: return failure, never return a token or retry the same assertion. The client must use a new assertion; subject uniqueness remains intact. A component fault-injection test commits to real PostgreSQL then drops the receipt and verifies this rule.

Admission requires explicit resource, nonempty scopes, TTL 1–3600 seconds, issuance/new-client quotas, prefetch budgets, enabled `open_basic` and an operator-recorded key custody acceptance condition. A signature proves key control; it cannot remotely attest an arbitrary client's confidential custody environment. There is no AWiki brand shortcut or per-client preregistration requirement. Issuance quotas serialize across replicas under the policy row lock. The accepted custody condition belongs in deployment records, never in client self-reported metadata.

## Operations and recovery

Use an administrative database role for migrations/configuration and a separate runtime role with no CREATE/ALTER/DROP. Runtime SQL needs SELECT and relevant INSERT/UPDATE/DELETE rights, including SELECT FOR UPDATE on policies. Keep secrets in a protected environment or mounted secret manager. The compose file is a controlled reference deployment; its initial database owner is for setup and must be replaced with least-privilege credentials before exposure. AS and RS are independent processes; the RS needs no database credentials.

`npm run admin -- block`, `unblock`, `disable-grant`, `cleanup`, and `invalidate-recovery` are real scripts. Scope their environment to the intended issuer/database. Cleanup deletes expired replay, metadata, minute/hour buckets and tokens expired for over a day, retaining clients, bans, grants and audit facts. It cannot reset live limits or unblock clients. Audit retention is an operator storage policy; application logs never print token/assertion/key/Basic headers.

After database restoration, isolate ingress and run `invalidate-recovery`: all policies become disabled and generation increases. Reconcile the newest trusted bans/revocations/policy facts before explicit policy configuration. If replay completeness cannot be established, keep traffic isolated for at least the complete worst accepted assertion window: 5 seconds allowed future iat + 60 seconds lifetime + 5 seconds expiration tolerance = 70 seconds, with an operational margin (71 seconds in the owning component) and verify trusted time. Lost bans or revocations require trusted reconciliation or continued refusal; waiting for token TTL alone never authorizes reopening. The earlier unit/component checks verify disabled policies and old-token invalidation. The process-recovery component additionally performs actual pg_dump/restore into another owned database and a real 71-second quarantine, including the valid future-iat edge; it remains a test-only module/runbook drill, not production deployment, an independent durable security witness or automatic malicious-DBA rollback detection.

Readiness checks schema plus configured fetch budgets for AS, and authenticated inactive-token introspection for RS. AS, database, RS credential or introspection-source failure is fail-closed. No remote deployment, production key custody review or full product acceptance is implied by component test success.
